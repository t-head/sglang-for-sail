# PPU Serving Recipe & Preset Authoring Guide

This guide defines the authoring contract for `test/ppu/recipes/` (`ppu-serving/v1`)
and `test/ppu/policy/` (`ppu-test-policy/v1`) in **SGLang for SAIL**. For the live
generated CI matrix and full serving preset catalog, see [README.md](README.md). For
cluster runner provisioning and workflow labels, see
[`scripts/ci/ppu/README.md`](../../scripts/ci/ppu/README.md).

## 1. Directory Layout & Single Source of Truth

| Path | Ownership | Contents |
| --- | --- | --- |
| `test/ppu/recipes/<org>/<model>.yaml` | Framework serving config | `sglang.launch_server` arguments, allowlisted serving env vars, precision variants, hardware overrides, and named presets |
| `test/ppu/policy/models/<slug>.yaml` | CI execution policy | Which variant/preset/hardware runs in PR `fast_sanity` or Nightly `model_sanity`, dummy/layer rules, GSM8K & microbench stages |
| `test/ppu/policy/datasets/<id>.yaml` | Evaluation dataset contract | Dataset version, few-shot count, filters, and expected sample count |
| `test/ppu/golden/accuracy_<key>_890p.json` | Accuracy reference | Reviewed GSM8K reference score and tolerance band (`±0.02`) per `golden_model_key` |
| `test/ppu/README.md` | Auto-generated (never hand-edit) | Generated by `python3 -B scripts/ci/ppu/ppu_recipe.py render-matrix --output test/ppu/README.md` |

Every serving parameter belongs in exactly one place: the model's `ppu-serving/v1`
recipe YAML. Every CI execution, router, benchmark, and dataset switch belongs in
`test/ppu/policy/` or the orchestrator runner. Do not introduce bespoke schema versions
for PD disaggregation or lightweight performance suites—express serving roles via
paired `pd_prefill` + `pd_decode` or `prefill` / `decode` / `decode_ep` presets in the
canonical model recipe.

## 2. Recipe Boundaries (What Must Never Appear in Recipes)

A serving recipe describes **only** how to launch `python3 -m sglang.launch_server` for
a public model. `scripts/ci/ppu/ppu_recipe.py validate --all` fails closed on the
following violations:

- **No runner- or policy-owned flags**: Never hardcode `--model-path`, `--model`,
  `--tokenizer-path`, `--served-model-name`, `--host`, `--port`, `--disable-radix-cache`,
  `--enable-prefix-caching`, `--no-enable-prefix-caching`, `--load-format`,
  `--enable-metrics`, or `--config`, and never set `num_hidden_layers` inside
  `--json-model-override-args` directly in a recipe. The runner injects endpoint flags,
  `--enable-metrics`, prefix-cache controls, dummy weights, and layer overrides from the
  active policy tier.
- **Canonical hyphenated CLI flags & valid SGLang values**: Every CLI option must use
  hyphenated spelling (never underscore options), `--mem-fraction-static` must be a
  finite float in `(0.0, 1.0]`, `--attn-dp-size` must be used instead of deprecated
  `--enable-dp-attention`, and `--reasoning-parser` / `--tool-call-parser` must match
  installed `sglang.srt.server_args.ServerArgs` choices (for example, `--tool-call-parser
  glm47` and `--reasoning-parser glm45` for GLM-5.3).
- **No client workload or router settings**: Do not put input/output sequence lengths
  (ISL/OSL), concurrency lists, prompt counts, `sglang_router.launch_router` flags, or
  sampling/dataset parameters in serving recipes.
- **No runtime-mode or host-specific environment variables**: Variables such as
  `HF_HOME`, `HF_HUB_OFFLINE`, `TRANSFORMERS_OFFLINE`, `CUDA_VISIBLE_DEVICES`,
  `SGLANG_USE_MODELSCOPE`, `SGLANG_WARMUP_TIMEOUT`, `VLLM_SERVER_DEV_MODE`, or
  `VLLM_USE_MODELSCOPE` are forbidden in recipes. Lower-level runtime/SDK variables
  (`DG_*`, `HGGC_*`, and `SGLANG_NSA_DUAL_STREAM`) are allowed only when explicitly
  declared in `ppu.external_env`.
- **No private infrastructure or unreleased models**: Public recipes must never contain
  local/shared filesystem paths, internal domains or mirrors, IPv4 literals, physical
  hostnames, physical RDMA/IB NIC interface names, credentials, or non-public model
  identifiers. Use logical `ppu.assets`, public Hugging Face `owner/name` repo IDs, and
  topology placeholders instead.

## 3. Hardware x Precision Binding Contract

Each target T-Head Zhenwu hardware family supports native `bf16` alongside its
hardware-specific quantized precisions:

| Hardware ID | Device Name | Allowed Variant Precisions |
| --- | --- | --- |
| `zhenwu_m890` | Zhenwu M890 (`ZW-M890P`) | `bf16`, `mxfp4`, `mxfp4_fp8`, `fp4`, `fp8`, `fp8_channel`, `fp8_block`, `w8a8_fp8`, `w4a4_mxfp4` |
| `zhenwu_810e` | Zhenwu 810E (`OAM-810E`) | `bf16`, `int8`, `w8a8_int8`, `w4a8_int8` |

- `bf16` is supported across all Zhenwu hardware families and is permitted for smaller
  or moderate-sized models that fit cleanly in `bf16` (for example, `Qwen/Qwen3.8-27B`).
  Omitting `hardware:` on a `bf16` variant keeps it portable across both `zhenwu_m890`
  and `zhenwu_810e` (both hardware targets are expanded in `validate --all` and listed
  in the catalog even without `hardware_overrides`); set `hardware:` on the variant or
  preset when pinning to a specific chip family.
- For large flagship models (100B+ / MoE), prefer native quantized precisions
  (`mxfp4`/`fp8` on `zhenwu_m890`, `int8` on `zhenwu_810e`) for serving and performance
  presets.
- A single model recipe YAML can host `bf16` and multiple quantized variants across both
  hardware families. Use variant-level `hardware`, `topology`, `assets`, `hf_model_id`,
  `golden_model_key`, and `served_name` overrides so each checkpoint resolves cleanly
  without duplicating recipe files.
- Every preset must match at least one compatible variant by hardware (and optional
  `variants:` allowlist). Cross-binding a `zhenwu_m890` preset/policy to an `int8`
  variant or a `zhenwu_810e` preset/policy to an `mxfp4`/`fp8` variant is rejected.

## 4. Standard Preset Slot Vocabulary & Topology Placeholders

Use the canonical four-scenario preset vocabulary below so serving layouts stay uniform
across models and frameworks:

| Slot | Topology `kind` | Purpose | Required SGLang Flags & Placeholders |
| --- | --- | --- | --- |
| `prefill` | `single_node` (`nodes: 1`) | Prefill-optimized single-node layout (e.g., `spec_decoding: false`, `--disable-prefill-cuda-graph`) | None (placeholders, multi-node flags, and `--disaggregation-*` flags forbidden) |
| `decode` | `single_node` (`nodes: 1`) | Decode-optimized single-node layout (e.g., TP8 with NEXTN / speculative decoding enabled) | None (placeholders, multi-node flags, and `--disaggregation-*` flags forbidden) |
| `decode_ep` | `multi_node_ep` (`nodes >= 2`) | Multi-node Attention-DP + Expert-Parallel decode layout (e.g., 4-node `--tp-size 32 --attn-dp-size 32 --moe-a2a-backend deepep`) | Must enable expert parallelism (`--ep-size > 1` or `--moe-a2a-backend != 'none'`), match full topology capacity (`DP * TP * PP == nodes * devices_per_node` with `--dp-size 1`), and wire `--nnodes <nodes>`, `--node-rank "{node_rank}"`, and `--dist-init-addr "{master_addr}:{master_port}"` |
| `pd_prefill` + `pd_decode` | `pd_disagg` (paired roles `prefill` + `decode`) | Disaggregated prefill/decode server pair behind `sglang_router.launch_router --pd-disaggregation` | Must be declared as a pair with `--disaggregation-mode prefill` / `decode`; for `mooncake` (default), wire `{kv_ip}` via `SGLANG_HOST_IP`, `{ib_devices}` via `--disaggregation-ib-device`, and `{kv_port}` via `--disaggregation-bootstrap-port` on `pd_prefill` (`pd_decode` receives prefill bootstrap endpoints per request from `sglang_router` and must not set `{kv_port}`). Sub-node splits (such as 4P + 4D on an 8-card node) set `devices_per_node: 4` on each role |

Specialized single-node slots already in use by existing recipes (`dp_ep_low_latency`,
`prefill_long`, `eval_longctx`, `decode_nographs`, `model_sanity`, `tp8`) remain accepted
for compatibility; prefer the canonical four-scenario vocabulary above for new models
and migrations.

### Placeholder Validation Contract

Supported topology placeholders are `{master_addr}`, `{master_port}`, `{node_rank}`,
`{kv_ip}`, `{kv_port}`, and `{ib_devices}`. During `validate --all`, `ppu_recipe.py`
expands 100% of compatible `variant x preset` combinations, substitutes safe typed
loopback/dummy values (`localhost` loopback, `29500`, `0`, `8998`, `rdma0`), and
validates CLI syntax, JSON objects, environment allowlists, SGLang world size
(`DP x TP x PP` with `--attn-dp-size` / `--attn-cp-size` / `--ep-size` divisibility
inside `--tp-size`), multi-node `host:port` rendezvous addresses, Mooncake
disaggregation wiring, and public redaction rules.

## 5. Three-Tier CI Gate Admission Rules

Adding a variant or preset to a recipe does **not** automatically allocate hardware CI
runners. Promotion follows three tiers:

1. **Tier 1 — Static Expansion & Catalog (Mandatory, 100% coverage)**
   Every compatible `variant x preset` must pass `ppu_recipe.py validate --all`, pass
   real `ServerArgs` argparse checks in candidate runtime verification, and appear
   automatically in `test/ppu/README.md` under
   `## Registered Serving Presets (Benchmark & Disagg Catalog)`.
2. **Tier 2 — PR `fast_sanity` (Selective single-node Zhenwu M890 execution)**
   Create or update a `test/ppu/policy/models/<slug>.yaml` `fast_sanity` entry only
   when **both** conditions hold:
   - Hardware is `zhenwu_m890`, `topology.kind == "single_node"` (`nodes == 1`, width in
     `{2, 4, 8}`), and the target `hf_model_id` snapshot is confirmed present in the
     runner offline HF cache; and
   - The preset covers a distinct operator, parallelism, or feature execution path.
   The single-node CI selector (`scripts/ci/ppu/recipe_select.py`) automatically skips
   `nodes > 1`, `pd_disagg`, oversized policies exceeding the single-node 8-card Zhenwu
   M890 runner limit, and non-M890 (`zhenwu_810e`) entries, while failing fast if any
   unrunnable slug is explicitly requested in `--model-filter`. Keep `zhenwu_810e`
   variants catalog-only until 810E storage and runners are ready, and keep
   `multi_node_ep` / `pd_disagg` static-only until multi-node / PD K8s CI is onboarded.
3. **Tier 3 — Nightly `model_sanity` (One GSM8K gate per ready mainline precision)**
   Maintain one full-dataset GSM8K + microbench `model_sanity` policy per ready mainline
   checkpoint (with a reviewed golden under `test/ppu/golden/`), ensuring all stages in
   `tiers.model_sanity.stages` agree on `preset` and `cache: enabled`. Do **not**
   duplicate Nightly GSM8K runs for serving-parameter tuning presets.

## 6. Reference Exemplar & Local Verification

Use [`test/ppu/recipes/zai-org/GLM-5.3.yaml`](recipes/zai-org/GLM-5.3.yaml) together
with [`test/ppu/policy/models/glm-5.3.yaml`](policy/models/glm-5.3.yaml) as the #0
full-scenario reference exemplar.

Run these commands from the repository root before opening or updating a PR:

```bash
# 1. Validate all recipes, policies, datasets, and 100% variant x preset expansions
python3 -B scripts/ci/ppu/ppu_recipe.py validate --all --sglang-parser skip

# 2. Validate against the real SGLang ServerArgs parser (inside an SGLang runtime)
python3 -B scripts/ci/ppu/ppu_recipe.py validate --all --require-sglang-parser

# 3. Regenerate and verify test/ppu/README.md
python3 -B scripts/ci/ppu/ppu_recipe.py render-matrix --output test/ppu/README.md
python3 -B scripts/ci/ppu/ppu_recipe.py render-matrix --check

# 4. Run CPU unit tests covering recipes, selector, and workflows
python3 -B -m unittest discover -s scripts/ci/ppu -p 'test_recipe*.py'
node --test scripts/ci/ppu/test_ppu_approval.cjs
```
